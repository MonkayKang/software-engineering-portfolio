## Week 3 Reflections

### For a step by step what re-work is triggered
1. Change Request is raised
   - Client Formally Request a Change
   - Project manager access the scope, risk, and cost of the change
2. Requirements from Month 1 are reopened
   - The one month requirements are now missing certain elements
   - Requires speifications
   - Acceptance Criteria
3. Requirement sign-off is repeated
4. Approved Design is revisited
5. Design sign-off is repeated
6. Existing implementation is reworked

###  If they were working in 2-weeks increments
1. Change Request is Raised
2. Change is added to the backlog
3. Prioritize the feature
4. Refine the requirements
5. Updated the affected design
6. Develop the feature
7. Implement the feature

### Comparing the two
- When analyzing the cost and effort of the change of each approach, the two weeks increments is the most cost-effective and less effort when implementing the new change. This is because the original waterfall method makes it so when the change is implemented late, everything must go back to the start where as if it was two weeks increments, then they can adjust to the change.

## Task 2
### 3 Weakness
1. Requirements are verbally communicated rather than documented
   - Both, since it reflects from the lack lack of absence of any process and was therefore communicated verbally and that a light-weight agile process could have caught and prevented this weakness by creating documented user stories and reviewed before the next phase.
2. Code is diretly pushed to the main branch rather than a local one before review
   - A agile process method would have caught and prevented this mistake because it is built with the flexibility with change and because it requires the review and approval before being committed to the main branch.
3. Testing consist of one developer who tries it once and moves on
   - This weakness is due to lack of process as the developer can claim that he did indeed reviewed it, but because there was no process or since it was independent, then this weakness would have still presented itself
  
**The first concrete, low-cost, improvement I would do first is having user stories and acceptance criteria as this not only sets the goals or objectives, but also a document of items that can be peer reviewed and changed. It must have doumentation so that others can use it as a reference and to be used as peer evaluation and catch weakness**
