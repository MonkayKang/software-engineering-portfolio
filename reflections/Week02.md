# Week 2 Reflections
### Brief A: Aegis Flight-Control Software Update
I believe that the best software development for this project is spiral. The reason for this is because this is a large scale project that is very critical. Lives are at stake due to it involving a fault sensor on an entire fleet of airplanes and, the cost of a field-discovered defect is 
extremely high. Because it needs to meet airline safety regulations and is mission critical, the spiral method allows for risk to be managed early and because of the design being large scale, errors and weak analysis are eliminated early in the development. Also, the client organization has a large, well resourced department that has no competitive pressure to release early. Each stage of the spiral is documented and planning is built in every single loop. One risk that could be present with this model is that it heavily relies on good risk assessments. This is because if this risks are missed, then the software will be continually developed with those same risks.

### Brief B: Riverside Bakery Marketing Website
For this project, I would use the Reuse-Oriented Software Engineering method. This is because of the limited budget of the client and wants the software to be live within three weeks. There is no safety or regulations dimensions and because the owner tends to change her mind on visual details, it will not cost a lot of both time and money to implement those changes. Finally, the technical aspect of the desired software is low and does not integrate with any other system making it ideal for a single application. The one risk of doing this method is that you lose the control of the system evolution since most of the components are reused updated by someone else. This means that if the client wishes to update to a new homepage, then it will only happen with the current tools at hand.

### Brief C: CampusCircle Community App 
For the community app, my approach would be to use the Iterative Development method. I believe this because the "founders" have a rough idea of the software core features but they expect it to change drastically when students starts to use it. This means that user feedback is important and each phase works with the feedback. It let's them to test out the software before the final product and improved step by step so defects are found early. Because they wanted this software to be completed within a month, the Iterative method spends less time on documentation and more time to designing. This is perfect for the "founders" situations because there is no  formal regulatory requirement but basic data protection practice around user accounts is expected. One risk when it comes to using this method is because the core features are roughly thought out, that means costly design or development problems emerge later since not all of the requirements of the app is gathered upfront and only after all the user feedback is applied, that the design requirements get asked.

## Task 3 (Hypothetical Situations)
When developing a game with a team, I would use he waterfall method because of years of experience with it. The first phase when developing a game is defining. Requirements are laid out and planned accordingly, as well as being well understood. Each aspect or feature of the game has it own field/departments such as programmers or artist. This works well with the waterfall method because it allocates resources where it's needed, such as an artist creating sprites and artwork for the game while the audio producers design the SFX and the game audio rather than the entire team working on it. Each step and phase is clear with specific deliverables before the next step, which is very important in game design. There are times when things cannot progress because the prerequisite isn't present (Character Model so that the programmers can code it into the game). It also implies good habits of designing the product well before it is made to make sure that scope is kept and the team doesn't lose focus. These process do overlap sometimes such as the artists or animation team working with the programmers to understand how a character will function in the game and some of the design problems gets spotted early in the development. While one of the risk is that testing only happens in the end, there is some testing that happens when developing such as code functionality and SFX but user feedback only appears near the end of the development.
